## 0. 第一小时：建立可信基线

先解压到一个新的、当前用户可写的目录，例如 `C:\Dev\Baseline-Handoff`。不要覆盖原仓库，不要删除原仓库修改，也不要再反复解压损坏的源包。

在本包 `baseline-club` 目录运行：

```powershell
node tools/run-bounded.mjs 30000 node tools/check-package.mjs
node tools/run-bounded.mjs 30000 node tools/build.mjs
node tools/run-bounded.mjs 30000 node tools/verify.mjs --baseline
node tools/run-bounded.mjs 15000 node tests/physics.mjs
node tools/run-bounded.mjs 1800000 node tools/serve.mjs
```

在浏览器打开 `http://127.0.0.1:5173/`。首次不用 `npm install`、不用 Blender，不用下载任何运行素材。逐个确认主页、人物、发球机、对手对战、动作室、设置、关于能进入。

**通过标准：** 三个入口文件确实存在（`src/app.js`、`tools/build.mjs`、`index.html`）；两个人物和六个基础动作数据可解析；恢复后 HTML 哈希匹配；本轮基本测试通过；浏览器打开没有致命错误。否则先保留日志定位，不扩需求。

然后本地 Agent 检查原仓库的 `git status`、PR head 和未提交修改，将恢复目录与仓库中的 `baseline-club/` 做路径级对比。只合入需要的源码、资产、构建工具和文档，不用镜像删除覆盖。**本次不改 `.github/`、不触发或依赖 Actions、不自动 push。** 旧 workflow 变更需要用户另行授权才能处理。

## 1. P0：人物艺术与变形质量（第一主线）

### 1.1 先分清是源资产差，还是转换毁了它

现在已有 Rain/Snow，不再回退椭球、胶囊或程序拼人。原始人物可用也不代表当前转换质量达标。必须做同一角色的三组对照：

- Blender 原始角色，在中性灯光下的正面、侧面、背面、三分之四视角；
- 当前导出 GLB，在中性背景下的同角度；
- 游戏实际镜头，白天与傍晚各一组。

对比头身比例、面部与眼睛、发型轮廓、手指握拍、运动服结构、鞋、UV、材质、肩胯轮廓。**不要用增加面数或更强 Bloom 掩盖建模问题。** 目前原素材日常服装也不等于最终网球服；需要在保留高质量人物基础上做一致的运动造型。

### 1.2 拆开“动作来源骨架”和“人物变形骨架”

Tennis-MoCap 是 18 关节来源，不代表角色也只能有 18 个 deform bones。当前转换把很多权重压到 18 骨骼，是明确风险。应保留角色合理的锁骨、肩部、上臂/前臂扭转、脊柱、颈部、髋部、足部结构，以及需要的手指/眼睛/辅助发骨。

建立 `source skeleton → retarget mapping → deformation rig` 显式映射；处理 A/T pose、骨骼局部轴、米制尺度、角色前向、root motion。所有缩放和 rest pose 修正放在可追踪的离线转换，不在浏览器里临时对每帧骨头瞎补。

需要的 corrective shapes 可以烘焙或保留为有限 morph targets。不要把 Blender 控制器、约束、驱动器存在当作浏览器自然支持它们；导出后逐项检查变形是否保留。

### 1.3 人物验收才决定这一阶段能否结束

六类基础挥拍分别检查准备、引拍、接触、随挥、回位；用正面和侧面检查主要动作，极端低球/高球/双手反拍必须覆盖。检查脚底滑动、肩膀塌陷、手穿拍、拍柄漂移、衣物穿体、脸和头发突变。

**通过标准：** 用户能在角色近景中认可造型；正常游戏镜头没有明显破坏观感的上述问题；同一动作导出前后相位、握拍、足底方向一致；源模型、转换脚本、输出 GLB、截图和素材来源可以对应。允许保留量化的轻微问题清单，但不能拿“所有坐标 finite”宣称艺术质量达标。

**停止条件：** 同一转换失败两次，先退到单人物/单动作最小案例定位映射；不能因此重做整个球场，也不能默认换回粗糙模型。原始 `.blend` 下载失败时继续使用现有 GLB 做对照和管线审计，将下载链接及缺口记录下来。

## 2. P0/P1：动作资产、步法与衔接

先保持当前被认可的正反手动作节奏，补完最影响可信度的移动，而不是追求动作数量。

第一批：ready / split-step、左右侧移、前后跑、启动/急停、击球后回位。接着补跑动击球、伸展救球和高低击球；发球、高压、截击再接入完整来球场景。优先可商用社区素材；新增来源要先记录许可，不要求用户自己动捕。

为每个动作定义：来源、帧区间、采样率、rest pose、准备/接触/结束时刻、惯用手、允许高度和横向范围、脚接触标签、root motion 类型。现有六个片段已在 `assets/motions.json` 中，不应当作六份完整比赛行为。

发现原始正手 BVH 声明 479 帧而有 480 行：先比较尾行是否重复、源文件是否存在已知格式问题，再在导入器明确采用声明帧数或完整数据行，写入报告。**不覆盖原始字节、不擅改原 SHA。** 当前烘焙片段不需要因此重做。

**通过标准：** 从静止、跑动、急停到正反手可以连续播放；接触瞬间不因跨 clip blend 丢失手柄位置；root motion 与程序位移不重复；脚锁定有可测误差。每个新增动作必须有实际可触发的游戏场景，不能只有选择菜单。

## 3. P1：统一击球模型——落点是结果

当前 `automatic()` 有相对速度反射思路，但拍面 normal 和 racketVelocity 主要靠公式构造，还含最小纵向速度保底，因此它是**物理启发式游戏模型**。先保留可玩基线，然后有对照地改进，不宣传“已经完全符合真实物理”。

### 三层职责

1. **输入/意图层：** 跑位、提前/延后挥拍、蓄力、击球类型、可选大致方向。自动模式不接收精确落点。手动模式接收区域或目标，用于生成可达的挥拍/发射意图。
2. **接触层：** 取实际动画相邻采样的拍头速度、拍面世界法线、相对来球速度、触球位置、甜区偏差、动作相位；生成出球速度和旋转。离散帧穿过球拍需扫掠/连续判定或受限时间窗，不硬要求站圈内。
3. **飞行层：** 同一套固定步长积分负责重力、阻力、旋转升力、触网、地面摩擦/反弹。预测辅助和 AI 共用它；不能在飞行中把球吸向目标或悄悄抬高以保证过网。

游戏宽容度单独命名为 assistance：如小范围接触纠偏、动画时间微调。记录纠偏距离和毫秒数，提供开关。严格模式取消兜底；不要把兜底速度、必中修正混进“纯物理”。

时机不是通用的“晚击一定斜线”：惯用手、正反手、站姿、拍面共同决定方向。测试左右手或镜像场地时的符号约定。球拍参数未来映射到反弹、旋转/甜区、挥拍惯性等可解释变量，**在模型稳定之前不做复杂调校 UI**。

**通过标准：** 固定输入和种子能重复；改变击球时机/拍面/偏心/力度会合理改变速度、旋转和落点；同一出球状态在玩家、CPU、预测器中一致；长帧不穿网；手动目标不能越过当前可达约束；误击、下网、出界都能自然发生。

## 4. P1：球生命周期、辅助与难度

### 球生命周期

分离“本分结束”和“球的可见性”。建议：live → dead-airborne → dead-bouncing → rolling → sleeping → delayed-recycle。计分只触发一次；漏球、第二次落地或触网后仍继续运动。

现有实现是固定 19–21 秒淡出，并非睡眠后才回收。下阶段补 `sleepAt` / `retireAt` 与显式最短保留时间；先回收离镜头远的已睡眠死球，数量上限是安全兜底，不让刚漏掉的球立刻消失。死球降低更新频率，但不再影响本分计分或被误击。

### 辅助拆分

落点圈、推荐站位、来球轨迹、可击窗口是显示辅助；自动跑位、自动时机是控制辅助，两组独立。提示不是强制区域，预测显示可以有合理误差/透明度，但不要偷偷用另一套飞行公式。

### 难度拆分

对手难度改变反应、选球风险、速度/角度、旋转、恢复；发球机可独立调球速、左右角度、深浅、旋转与间隔。玩家移动能力、击球容差与视觉辅助另设，避免选 Pro 就毫无说明地削弱角色。

**通过标准：** 关闭所有显示辅助不改变相同 seed 下的球路；漏球后观察得到后续反弹和滚动；切换难度不改重力；设置进入/关闭不丢一分；预测落点与实测落点差可统计；触屏 UI 不遮挡来球、球员或拍头。

## 5. P1/P2：三位对手与比赛循环

先用现有三个风格，不继续无限增加角色。Rowan 以深球和稳定回合为主；Kai 高球速、高风险、移动相对一般；Noa 用变线、长短、切削和上网制造不同压力。

不用大模型在线决策。采用：有限感知与反应延迟 → 可达击球计划 → 战术候选评分 → 同一动作/接触模型 → 回位。对手必须受速度、加速度、动画准备时长、体力/平衡与失误约束，不能瞬移或在到不了的位置回球。

不依靠强制送分实现风格；同一组固定来球和种子，统计平均回球速度、深浅、线路变化、非受迫失误、网前比例、平均回合长度。让对手差异能从回合里感受到，不只是名字和衣服不同。三位 AI 可以暂时共享 Rain/Snow 两套基础模型，第三套原创外观不是本阶段先决条件。

**通过标准：** 每位对手能从开场到 7 分领先 2 分结束完整打完；玩家可赢也可输；不中断的连续对拉；同一规则处理双方出界/下网/二跳；暂停、回放、重开不会重复计分；结束可换对手而不泄漏资源。

## 6. P2：模式、界面与操作收口

保留并完整验收：对战、自由练习、Target、Endurance、动作室、上一拍回放。主页明确“对战/训练”，不把所有设置摆成工程调试台。输入帮助首次可见，之后可关闭。作品名称使用 Baseline Club，不再以 court-study 对外展示。

默认自动落点；手动目标为独立设置。自动模式仍需可理解的方向意图，不把“没有任何选择，只能看动画随机回球”误当真实网球。可通过身体朝向、横向输入或击球类型提供约束内的选择。

版权、来源、素材适配说明统一在关于，底层许可证文件保留。开发者遥测置于调试开关，不常驻玩家界面。

**通过标准：** 首次进入能在一分钟内开始练习；手机横竖屏能移动/击球/暂停；蓄满保持，指针取消/失焦不会卡住输入；每个模式都有结束/重开；回放恢复同一球与角色状态。

## 7. P2：渲染与性能，只优化实际瓶颈

先记录角色独立视图、单人发球机、双人对战的 CPU / GPU、draw calls、纹理显存、三角面、内存与帧时间。对比渲染与动作/预测的 CPU 花费；不能仅凭 FPS 猜是模型太多面。

优先处理材质和贴图正确性、角色局部光照与接触阴影、过多材质 draw calls、冗余不可见身体部件、姿态/预测临时对象分配、重复反序列化人物、预测器调用频率。之后再做 LOD、压缩纹理、资源延迟加载等。所有优化都要对照人物近景，不能为了性能把核心人物削回占位水平。

建议验收目标（不是已测结果）：在你的 RTX 4060 桌面与选定 1080p 画质下追求稳定 60 FPS；帧预算按 16.7 ms 定位，另看 P95/P99 与 1% low。手机按指定机型分中高档，连续 10–15 分钟记录温度/帧时间趋势；低配模式先牺牲阴影/后处理/环境，而不是破坏关键人物轮廓。

桌面和至少一台 iOS / Android 真机通过之前，不把本项目标成最终 release。Safari / Firefox 验证要单独报告，不把 Chromium viewport 模拟当成真机或 Safari。

## 8. P2：发布与工程资产

源码以 `src/`、`tools/`、`assets/` 明文结构提交，压缩包是交付副本，不是唯一源码载体。生成单文件 HTML 满足当前交付方式；以后网页部署可加多文件模式，二者从同一源码构建，不维护两套游戏。

完成版本应输出：最终 HTML、可解压工程 ZIP、SHA256SUMS、素材 manifest、源码 revision、验证报告、已知问题。先在一个全新目录解压，核对哈希，再从包内构建和运行。GitHub 上传失败不阻塞交付；PR 写明哪些代码已上去、哪些二进制已缓存、缺失资产的 URL/hash/操作方式。

本地测试命令、依赖缓存和构建脚本独立存在，**不需要也不擅自修改 GitHub Actions**。历史 workflow diff 不在这轮恢复里自动清理。

**通过标准：** 新机器按文档能获得入口文件；ZIP 校验可重复；文件修改后重新生成的报告明确对应新 SHA；无新外部运行资源依赖；连续完整比赛、多模式切换和真机门槛通过；用户认可人物质量。

## 9. V1 之后，才考虑的事项

按需求价值择一推进：球拍调校 → 完整网球计分/盘制 → 更多动作/场地 → 手机 PWA / App 包装 → 联机。角色成长、职业生涯、商城、联网账号、复杂布料、全脸表演不进入当前主线。只有实际 Web 平台限制已经被性能和发布需求证实时，才重新评估原生引擎迁移。

## 10. 每个阶段的执行方式

一次只交付一个可验收目标；不要把 8 个阶段合并成一次无法结束的大任务。日常基本测试 10–20 秒模拟即可，完整长测只在候选版本做一次；图像检查至少覆盖当前修改影响到的近景与极端姿态。

建议命令预算：静态与构建 30s、物理单测 15s、浏览器 smoke 60s、单场景截图 90s；Blender 每人物任务先 180s，有持续可测进度才另行调整；每项下载先连接 10s / 总量 120s / 最多一次重试。外层工具超时要更长，不要在 35s 外层命令里塞 180s 的子任务。超时标记为未完成，不重新从头下载全部资源。

**最终方向不变：高质量人物是核心；资产、动作、物理、AI 与工程交付形成同一条可验证链路。**
